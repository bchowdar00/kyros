# BTC signal definitions

One hundred ninety-three V1 definition files define the BTC signal surface; 190 of them are published (processor-backed), the three refuse-closed identities `btc.multi.oracle_dispersion`, `btc.pyth.price_momentum` and `btc.pyth.price_volatility` being defined ahead of their processors. Pre-production revisions replace their sole V1 definition in place; superseded duplicates are not retained in the active repository.

Blended spot set (`btc.external.*`, computed from Coinbase and Kraken feeds together, ready only when every adopted venue is fresh):

- reference and return state: `spot_reference`, `realized_volatility`, `cross_venue_dispersion`, `micro_momentum`;
- trade state: `vwap_deviation`, `aggressor_flow`, `absorption_state`;
- book state: `spot_microprice`, `actionable_depth_imbalance`, `order_flow_imbalance`, `liquidity_shock`;
- derived context: `early_move_fade_context`;
- technical analysis (C3a, ruling E51, on the blended reference midpoint): `atr`, `rsi`, `roc`, `ema_cross`, `macd`, `bollinger`, `zscore`.

Per-venue spot set (`btc.coinbase.*` and `btc.kraken.*`, one identity each, adopted 2026-09-02 under ADR 0024): `spot_quote`, `spot_microprice`, `actionable_depth_imbalance`, `liquidity_shock`, `order_flow_imbalance`, `aggressor_flow`, `vwap_deviation`, `realized_volatility`, `micro_momentum`, and — added the same day by that ADR's amendment — the four microstructure measurements `effective_spread`, `kyle_lambda_drift`, `sweep_detection` and `book_resilience`; C3a (ruling E51) added the same seven technical-analysis identities the blended set carries — `atr`, `rsi`, `roc`, `ema_cross`, `macd`, `bollinger`, `zscore` — computed on that venue's own midpoint ring, taking each per-venue spot set to twenty identities. Each reads only its own venue's ticker, book and trade inputs and is ready whenever that venue alone is fresh, warmed and valid, so one venue's fault no longer silences the other's readings. The blended `btc.external.*` reading of the same measurement is the reference layer and keeps its every-venue gate; a per-venue reading is never an input to a blended one. The `btc.binance.*` and `btc.bybit.*` venue namespace segments now carry twenty spot-sibling identities each (thirteen from B1, ADR 0028, plus the seven C3a technical-analysis identities) and twelve derivatives-lane identities each — the five B2 tier-1 families (ADR 0026) plus the seven C3a `perp_*` technical-analysis identities computed on that venue's perpetual mark series — so thirty-two per venue; both venues are rights-gated behind `SIGNALS_ENABLED_VENUES` (ruling R7) and do not publish on the default deployment.

Venue-scoped prediction set shared by both venues (`btc.polymarket.*` and `btc.kalshi.*`, one current identity per venue): `market_contract`, `prediction_quote`, `prediction_liquidity`, `prediction_trade_flow`, `window_delta`, `standardized_moneyness`, `fair_up_probability`, `executable_edge`, `pair_cost_state`, `venue_repricing_lag`, and `tie_rule_context`. The two venues settle on different benchmarks (Chainlink TWAP versus CF Benchmarks BRTI), so their measurements are deliberately separate identities and are never merged.

Polymarket-only prediction set: `settlement_anchor_state` and `oracle_divergence`. Each reads its own venue's resolving oracle (Polymarket the Chainlink BTC/USD 60-second TWAP, Kalshi the CF Benchmarks BRTI), so both venues now publish thirteen identities each (the Kalshi pair was added under wave B3).

Nine identities were adopted from `../candidates`: `pair_cost_state`, `venue_repricing_lag` and `tie_rule_context` on both venues plus the shared `early_move_fade_context` on 2026-09-01 (ADR 0023), and `settlement_anchor_state` and `oracle_divergence` on Polymarket on 2026-09-02 (ADR 0023 amendment). Each venue's pair-cost variant keeps its own verified fee model rather than sharing one, and `oracle_divergence` was re-homed from `btc.external.oracle_divergence` on adoption because it is computed per bound Polymarket market and published under that market's scope.

Every file declares exact inputs, fields, timing, staleness, arithmetic, and fail-closed readiness behavior. Until the first production release, every source and signal remains `1.0.0`; after release, a changed public contract requires a new version and an explicit compatibility decision.
