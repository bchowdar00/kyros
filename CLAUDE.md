# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Build & Run

### Server (Rust workspace — `server/`)
```bash
cd server
cargo build                    # exchange crate (default member)
cargo build --workspace        # exchange + strategy-compiler + signals crates
cargo run                      # run dev server on :8080 (same as -p exchange)
cargo test --workspace         # all tests, incl. compiler insta snapshots
cargo clippy --workspace --all-targets
```

Layout: `crates/exchange/` is the server binary (engine, bots, API, pricing,
automation). `crates/strategy-compiler/` is a pure library (IR → parse →
validate → lower → emit) with its fixtures under `tests/corpus/` and wire
schemas under `tests/schemas/`; the single entry point is
`strategy_compiler::compile()`, and `registry/tiny.json` is the venue contract
it validates against. `crates/signals-core/`, `crates/btc-feeds/` and
`crates/btc-signals/` are vendored from the signals prototype (feed adapters
and signal producers); the exchange declares them as dependencies but nothing
in `crates/exchange/src` uses them yet.

### Frontend (Next.js/TS — `frontend/`)
```bash
cd frontend
pnpm install             # install deps (Node 24, pnpm pinned in package.json)
pnpm dev                 # Next.js dev server on :3000 (set EXCHANGE_API_URL / NEXT_PUBLIC_API_URL in .env.local)
pnpm build               # production build (next build)
pnpm check               # format + lint + typecheck + tests + knip + icon drift
```

Layout: `frontend/` is the Next.js app itself (`src/`, `e2e/`, `public/`,
`next.config.ts`) and the pnpm workspace root; `frontend/packages/` holds its
workspace libraries (`ui`, `api`, `domain`, `money`, `testing`, `config`).
`pnpm typecheck` and `pnpm test` cover the app and then the packages.

### Development workflow
`./dev.sh` runs both. Or: the Rust server first (`cargo run` in `server/`), then the Next.js dev server (`pnpm dev` in `frontend/`) with `frontend/.env.local` pointing `EXCHANGE_API_URL` / `NEXT_PUBLIC_API_URL` at `http://localhost:8080` (see `frontend/.env.example`).

## What This Is

A live prediction-market demo running on real Bitcoin prices. Several BTC up/down market *series* run at once (a 2-minute and a 15-minute series, table in `server/crates/exchange/src/series.rs`), each a loop of back-to-back rounds: the strike is BTC's price when the round opens, and at close the real price decides YES (up) or NO (down). Every series has its own book, positions and bots; all of them share one balance per account. Single-canonical-YES-book model with signed positions, exact collateral accounting (total locked = OI × $1), four-case clearing (Open/Transfer YES/Transfer NO/Close). Accounts start with $1,000; balance is account-scoped so winnings roll into the next round.

## Architecture

### One `Exchange`, one `MarketEngine` per series, one lock
`Exchange` (`engine/mod.rs`) owns the shared `Ledger` (every account's cash and locked collateral) plus a `Vec<MarketEngine>`, one per row of the `SERIES` table. A `MarketEngine` (`engine/market.rs`) owns everything that is per-series: the book, open interest, per-order locks, recent fills, the current round and resolved history. Every trading entry point takes a `SeriesId`, routes to that engine and hands it the ledger; `SeriesCtx` bundles the two for callers that trade one series (bots, market maker, strategy executor). `Engine` is a permanent single-series facade used by unit tests.

The whole `Exchange` sits behind a single `Arc<Mutex<Exchange>>`. Bots, market makers, schedulers, HTTP handlers and strategy executors all take that mutex directly; lock holds are microseconds. There is **no** single-writer task and no command/event channel into the engine today. The two-lane ingress queue that would give the automation stack priority is specified in `agent_docs/automation-implementation.md` §3.7 and is not built.

Every account has an optional `home_series`. Bot and strategy sub-accounts are pinned to one series and the engine rejects their orders in any other; parent user accounts (`home_series = None`) may trade every series. Settlement in one series only sweeps orphaned sub-accounts homed in that series.

### Server (Rust — `server/crates/exchange/`)
Axum on Tokio. WebSocket streams under `/ws/*` (`price`, `book`, `trades`, `positions`, `accounts`; each carries a series parameter where relevant), HTTP routes under `/api`, health check at `GET /health`. CORS via `tower-http`. All money is integer `Tenths` (1/10 of a cent) — never f64.

### Frontend (Next.js/TS — `frontend/`)
Next.js 16 (App Router) + React 19 + TypeScript. Subscribes to the per-stream `/ws/*` sockets for real-time data (price ticks, order book snapshots, trade/activity feed, balance/position updates, market lifecycle/countdown) and derives every chart window from the server's per-series snapshot.

### Price feed task
Streams BTC/USD from Pyth Pro (Lazer) over WebSocket when `PYTH_PRO_API_KEY` is set (three redundant nodes, `real_time` channel, official `pyth-lazer-client`), falling back to Coinbase's keyless public ticker otherwise. Normalizes ticks into one rolling window **per series** (rounds of different lengths start and end at different times, so new clients get the right chart history), a global time-bounded velocity buffer that no round reset clears, and a broadcast channel of ticks plus series-tagged `MarketReset` events. Schedulers read `latest()` for strikes and resolution. Fully decoupled from trading.

### Market lifecycle schedulers (one task per series)
`scheduler.rs` spawns one task per series. Each waits for the first BTC tick, opens its series' first round with that price as the strike, then on its own interval (the series' `duration_secs`) calls `resolve_and_open_next` for its series: cancel every resting order in that book (refunding locks), decide YES/NO from close price vs strike, pay out winners, reset bot bankrolls, zero OI, open the next round with the close price as the new strike, reset that series' price window. There is no separate lock phase; cancellation happens inside resolution. One active round per series, so several rounds are open at once across series.

### Bots (per series, all run server-side as normal engine clients)
**Market-maker bot** — one per series. Continuously quotes bid/ask around fair value with configurable spread and size. Refreshes on price moves, skews to manage inventory. Guarantees tight spreads and instant fills.

**Trader cohorts** — one cohort per series (defaults 350 for `btc-2m`, 300 for `btc-15m`, overridable with `TRADER_BOT_COUNT_<SLUG>`, capped by the names file). Each bot is a funded account pinned to its series. Connected to the BTC price feed, they trade with a view (lean YES when BTC ticks up vs strike, NO when dropping). Heterogeneous: different reaction speeds, thresholds, sizes, aggressiveness, some contrarians. Seeded, so the population is reproducible across restarts.

Bots use the same engine calls as human users. No special-casing. They double as load/integration tests.

### Automation (strategies)
A user deploys a strategy into a funded **sub-account** (`engine/sub_accounts.rs`) homed in one series; the sub-account's position, collateral and PnL are isolated and money moves parent↔child only as plain transfers. A strategy is an IR document (`strategy_compiler::Strategy`, IR v0.3) plus an envelope; `POST /api/accounts/{addr}/strategies` compiles it against the generated registry (`api/strategy/compile.rs`), derives the home series from its instruments (`<slug>.current`), stores the record (`engine/strategies.rs`: source, envelope, params, compiled `Program`, `deployment_id = strategy_id:deploy_epoch`) on the new sub-account, and starts the deployment through the runtime manager; a compile failure returns 400 with the diagnostics and moves no money. PATCH pauses/resumes the deployment, DELETE stops it (cancelling its orders) before closing the sub-account, GET merges the record with the runtime's status. `POST /api/strategy` is a stateless compile-check over the same helper. The old OpenAI Block parser and its polling executor are gone; LLM authoring has to emit the IR document (not rebuilt yet).

The runtime is event-driven (`automation/{signals,sme,runtime,venue}`): the Signals Matching Engine deduplicates trigger conditions across deployments and wakes a deployment only on an activation; the interpreter turns an activation into an inert action batch; the deployment task runs the batch through the `Venue` trait and applies order fates from `ExecutionEvent`s via each intent's `on` table. All arithmetic is `rust_decimal`; the totality pins for division and the analytic builtins are documented on `automation/eval.rs`. `main.rs` wires it: `EngineVenue::install` puts the execution sink on the exchange before anything trades, `spawn_manager` runs deployments over `EngineVenue` (`automation/venue/engine.rs`, over `Arc<Mutex<Exchange>>`), the signal bus feeds the platform, and each scheduler sends `window_settled` then `window_opened` (market id and `<slug>.current`) after every transition, outside the lock. The engine side (`engine/events.rs`, `PlaceOpts` on `MarketEngine`) emits `ExecutionEvent`s only for orders carrying a `client_order_id`, supports IOC limits, `post_only`, `reduce_only`, `expire` and atomic `cancel_replace`; the sink is a synchronous callback so a settlement's cancel acks reach the runtime before the scheduler's settlement notification.

**Rate control.** A deployment is never paused for being busy. The platform delivers only activations (no per-subscriber signal-update frames), and the deployment task coalesces the activations queued behind the one it is handling: a run of consecutive same-cause activations (same fired set, same publishing signal, same session) collapses into the latest, so a maker behind a fast signal requotes once against the newest snapshot; any other frame ends the run and is processed in order. The one hard ceiling is `MAX_ORDERS_PER_SEC` submissions per deployment (`deployment.rs`); the excess is a local `envelope_violation` reject that follows the intent's `on.reject`. Both are counted (`coalesced`, `rate_rejects`) in the runtime status the strategy routes return. The account view is read once per activation and cached until a venue call or a lifecycle event. On the compiler side, `lint-requote-rate` warns when a `place`/`cancel_replace`/`target_position` block without a `then` is gated on an `if_true` + `immediate` trigger with no cooldown over a signal whose registry metadata declares `approximate_interval_ms` under a second; the exchange marks its per-event internals (`price`, `trades`) with `0`. For an `if_true` trigger, `rearm.cooldown` already means "at most once per cooldown, with the latest snapshot", so it is the throttle to reach for. Tests: `cargo test -p exchange automation::` (runtime, `fair-discount` on a real `Exchange`) and `api::strategy::` (routes against a real manager, including deploy → bus frame → order on the book, and deploy → lane message → order on the book).

**Public strategy templates** (`templates.rs`, files under `crates/exchange/templates/`, format pinned by the README there). Seventeen templates (eleven BTC, six NBA on `nba-h2h`), each a card (id, title, creator handle/username/portrait filename, prose for Run and Inverse), envelope ratios, per-series substitutions and two IR documents (`primary`, `inverse`; the inverse is its own document because outcome is a literal and the strategy id is a content hash). The files are embedded with `include_str!` and `TemplateCatalogue::load` stamps `{{series}}`, `{{spot}}` (from the boot `PriceSource`) and the substitutions per listed series, compiles all 46 documents against the generated registry and makes any diagnostic *or warning* a boot failure (exit 78); the compiled `Arc<Program>`s stay in `AppState.templates` so a template deploy never compiles on the request path. `GET /api/strategies/templates?series=` and `GET /api/strategies/templates/{id}?series=` (`api/templates.rs`) serve the cards: both sides with their prose and per-side `running`/`deployed_tenths`, combined counts and `runners`, from one walk over `accounts_iter` under the engine lock (`TemplateTally`: active sub-accounts whose record carries `template_id`/`inverse`, homed in the series; runners is the creator's portrait when the creator's own account runs it, since user accounts have no portrait file). Each side and the card also carry `ready` and `waiting_on` (`[{ signal_id, name }]`), from `Readiness::from_bus`: a side is ready when every id in its compiled `program.subscriptions` is usable on the bus, meaning `ready_since` is present **and** `ingest.published > 0` (the bus stamps `ready_since` before typing, so a lane signal whose frames all fail typing would otherwise read as ready while the platform has never seen a value); the card is ready when both sides are and `waiting_on` is their union. A deployment whose signal is missing or not ready never fires and never errors (a row reading an unpublished field is false, the interpreter skips blocks whose reads are absent), so the frontend hides such cards (`strategy-template.mapper.ts`), refuses Deploy in the open widget with the signal names, and polls the catalogue every fifteen seconds (`use-strategy-templates.ts`) so a lane warming up or degrading moves the column without a reload. The house still seeds every side, and a running deployment keeps running and stays in My Strategies when its signal degrades. `POST /api/accounts/{addr}/templates/{id}/deploy` (`api/strategy/template.rs`) takes `{ allocation_tenths, inverse, series? }`, derives the envelope with `templates::envelope_for`, and reuses the fund-and-start path of the authored route over the cached program, never compiling; an `Idempotency-Key` header replays the first deploy. At boot `house.rs` registers the house account (fixed address, username `Tiny`), credits it, and deploys both sides of every template on every listed series through the same in-process path (`HOUSE_SEED_ENABLED=0` skips it). Each house deployment is funded with `house_allocation(template_id)`: $8,000 to $64,000 in $100 steps, fixed per template by a stable FNV hash of its id (`stable_hash`), so the same on every boot and every series; the boot credit is the sum (`seed_credit`). It runs under `house_envelope`: the file's ratios with `loss_budget` cut to a quarter of the allocation (the risk gate enforces it as worst-case exposure, so at most a quarter is ever at risk) and `max_exposure_fraction` 0.5, through `deploy_template_side_with`; the HTTP route still uses the file's ratios. The cards route adds a **display crowd** to each side's `running` when `AppState.crowd` is on (`Crowd::enabled_by_env`, `HOUSE_CROWD_ENABLED=0` turns it off; the test builders leave it off): a pure function of template, series, side and the current minute, baseline 50 to 280 per card scaled linearly by the house allocation, split 40–60 percent between the sides by hash, plus a ±3 drift per side per minute; the real tally is added on top so a real deploy moves the number by exactly one, and `deployed_tenths` stays real. Tests: `cargo test -p exchange -- house` and the crowd tests in `api::templates`. Every document trades **both sides** (the primary takes whichever side fires; the inverse is a different strategy from the same family, never a mirror, since on a complementary book "Up cheap" is "Down rich"), sizes orders in dollars (`envelope.allocation * {{stake}} / price`, `{{stake}}` from the file's `order_fraction`), and is written to fit the matching engine: literal trigger rows shared across deployments, `if_true` + `immediate` for entries and exits (a `fresh_crossing` that goes true while a leg masks it is spent and never delivers), holding legs arming only their own exit. The exchange publishes `<slug>.current.delta.v1` (`automation/delta_signal.rs`: signed basis points from the strike, spot, strike, per feed tick) so a document prices the round with an `expr` row instead of joining spot to strike. The quoted outcome is per series (`series::is_quoted_outcome`, from the series table's first outcome: `up` on BTC, `home` on NBA); the venue translation, the risk gate's signed size and the runtime's fill-price complement all decide an order's frame from its outcome label, so NBA documents name `home`/`away` and trade the home book correctly. Tests: `cargo test -p exchange templates` (every template compiles clean on every listed series; the routes) and `cargo test -p exchange template_tests` (`src/template_tests.rs`: each template side deployed through the real handler, frames published, positions asserted on the real book).

**Signal ingest** (`automation/signal_bus.rs`, `automation/lane_bridge.rs`, `signals.rs`). Every signal enters through `SignalBus::publish`, which types the frame against the registry and hands it to the platform *first*, then keeps it as the latest frame and broadcasts it to `/ws/signals`; the frontend is deliberately second. The vendored lanes (spot, venue, prediction) are run by the supervisor in `signals.rs` with a stream hook (`btc_signals::stream_accounting::StreamHook`) that sends each stream-v3 message on one unbounded channel before its bytes reach the lane's output file; the lane bridge drains that channel: `signal_batch`/`snapshot` updates become bus frames under `<wire id>.v<major>`, and an `instance_status` (warming, degraded, unavailable, invalidated) updates the catalogue's readiness and clears the platform's snapshot for that signal, so predicates read it as unpublished until the next ready value. The platform task drains signal-side commands ahead of control traffic. The catalogue (`GET /api/signals`) carries per-signal `ingest` counters (frames published to the platform, frames the registry refused, last reason) and `ready_since_ms` (the bus stamps it when a signal's quality becomes ready and clears it on any other quality, so a card can say a strategy is waiting on a warming-up signal); a lane signal that publishes but never counts as `published` has a definition/field-set mismatch, and the bus warns about it once a minute. The lane output files remain the durable record (journals, checkpoints, replay); nothing reads them live. Not done: binding a market-scoped Kalshi/Polymarket instance to the series whose round it matches (today the newest instance wins under the signal id).

## Key Invariants
- All money in integer `Tenths` (1/10 cent). No floating point for balances or prices. BTC spot is the one `f64` (feed, strikes, fair value) and never touches the ledger.
- Prices are tenths-of-a-cent on a fixed non-uniform tick grid (`ticks.rs`): 0.1¢ steps in 0.1–3¢ and 97–99.9¢, 1¢ steps in between, 153 ticks, symmetric so every YES tick's NO complement is also a tick.
- One contract pays `Tenths(1000)` ($1). Per series, Σ locked collateral = open interest × 1000; across series, Σ engine `locked_total` = Σ `Account.locked` on the ledger. Zero-sum settlement.
- Four fill cases determined by both parties' signed positions: Open (new OI), Close (release OI), Transfer YES, Transfer NO.
- Account-scoped balance shared across every series, positions scoped per series — winnings roll into the next round of any series.
- A sub-account or bot never trades outside its `home_series`; the engine enforces it at order time.
